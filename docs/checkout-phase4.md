# Phase 4: persistent checkout and inventory reservation

## Inventory decision

`Producto.stock` remains available-to-sell inventory; `gestionStock=false` skips
physical reservation. No second stock collection/counter was introduced. Reuse of
the alternative controller's correct guarded `$inc` is centralized in
`inventoryReservation.js`. A Mongo session/transaction is mandatory. There is no
standalone/session-less fallback. The alternative controller now uses this helper.
All lines, the pending order and its reservation are committed together. Mongo
`withTransaction` retries transaction conflicts; no Stripe call is inside it.

## Persistent intent and indexes

App POST `/api/stripe/payment-sheet` sends `Idempotency-Key` alongside Firebase
Bearer authentication. UUID is generated by Expo Crypto, contains no identity and
persists in AsyncStorage per local Firebase user. Storage contains only UUID,
commercial-payload SHA-256 digest and submission flag, never address/token/secret.
Retries and remounts use the same key. Changes to input retain that key and are
rejected if Mongo already bound it to another payload. Explicit backend-confirmed
release/completion lets the next deliberate purchase generate a fresh key.

Order `_id` is the first 24 hex characters of SHA-256(JSON.stringify([UID,key])).
The existing Mongo `_id_` unique index arbitrates concurrent inserts on every
process; this is not `findOne` then unguarded `create`. Full key hash, verified UID
and normalized-payload hash are also checked to fail closed on collisions.
Addresses are trimmed, quantities combined and products sorted; coupon is uppercase.
Same key/different UID does not grant access to the other UID's order.

**New Mongo indexes: none.** `_id_` already exists and cannot contain duplicate IDs.
No historical orders or IDs are modified. A rare collision with historical data
fails owner/hash validation; never overwrites it. These deterministic ObjectIds no
longer encode creation time; use `createdAt` for chronology. No index/migration or
external command was executed. Expiration scans may need a separately reviewed
nonunique index for scale, not correctness. Order-number counter gaps from aborted
transactions are possible; no historical order is removed.

An intention is identified by its key: another device must carry/recover that same
key to join it. Local AsyncStorage does not automatically synchronize keys between
devices. A different newly generated key represents a different purchase, even if
items match. There is no claim of automatic cross-device cart-intent synchronization.

## Mongo and Stripe sequence

1. Normalize/hash payload and identify UID/key order.
2. In one transaction, find compatible existing order or validate Mongo products,
   calculate trusted prices, reserve each managed product with stock >= quantity,
   create pending order and reservation. Insufficient stock rolls everything back.
3. Persist Stripe attempt timestamp before external work.
4. Outside Mongo transaction create/replay Customer and PaymentIntent, each using
   stable Stripe idempotency keys derived from the persisted key hash. Request
   metadata/price/customer parameters remain stable, without fresh reqId/IP.
5. Persist PaymentIntent ID and amount. No client_secret is stored in Mongo.
6. Return only required PaymentSheet credential, order ID and pricing. Known
   intents are retrieved on replay; no new intent is created after reservation expiry.

Reservation defaults to 15 minutes, configurable by `CHECKOUT_RESERVATION_MINUTES`
(range 1–60). This bounds retry creation far below Stripe key-retention windows.
Permanent Mongo intent identity is not a TTL document and is never deleted.

## Reservation states

`none` (historical orders), `reserved`, `consumed`, `released`,
`reconciliation_required` (paid after release). Fields record reserved/expiry/
consumed/released dates, managed product quantities and release reason. The flag
`needsReconciliation` also represents unresolved Stripe preparation or a paid/
processing intent observed during expiration. Paid-after-release blocks payouts.

Release uses a transaction: read reserved state, restore all product quantities,
mark released/terminal. Two concurrent releases cannot restore twice. Financial
success and consumption happen in the same transaction; stock was already deducted
at reservation, so consume does not decrement it again. Duplicate signed success
or cancellation has no duplicate inventory effect. Refunded orders are not reverted
to paid by a later success event. Missing historical products make release fail
atomically instead of losing a partial restore.

## Expiration and failure safety

`getLifecycle().expire(100)` locates expired reservations. Operational CLI is
`node scripts/expire-checkout-reservations.js` from `backend-multi`. It is not
imported/started by HTTP, workers or a memory timer. A production scheduler must
invoke it repeatedly; no scheduler, worker or infrastructure was activated here.
Rows requiring reconciliation do not starve later ordinary expiration batches.
Runner logs checked/failed counts. An empty or fully successful batch exits 0;
any partial failure, connection/batch error or disconnect error exits nonzero.
Error output is fixed and does not include driver/Stripe messages or credentials.
Successful releases are not undone when another row fails. A later invocation
rechecks persistent reservation state, so completed releases are not repeated;
failed releases retain inventory and are retryable.

release within one minute. Stripe latency, failures and backlog affect that delay.
Use one scheduled job with no overlapping invocations; retain transactional
idempotency as protection against manual retries or process races. Do not run a
timer inside the HTTP API or enable payout workers to perform this task.

Before activation, separately approve the scheduler, its service identity,
transaction-capable Mongo connection, matching Stripe mode/account and secret
configuration. Do not reuse integration-runner credentials or databases. Never
place a URI or password in the command, logs or this document. The proposed job
has real effects: it may cancel/expire Stripe objects and return reserved stock.
Nothing in this document authorizes activating it or running it in production.

Supervision proposal:

- Alert immediately on nonzero exit or a timed-out/terminated invocation; retain
  sanitized counts, start/end time, duration and exit status for each run.
- Alert when no successful completion is observed for five minutes. Treat any
  external job timeout as failure; choose its duration after staging measurements.
- If `checked=100` persists for three invocations, investigate saturation. Counts
  alone cannot prove backlog: inspect oldest eligible expiry and remaining rows
  using an independently approved, read-only operational check.
- Separately monitor `needsReconciliation=true` and
  `state=reconciliation_required`, plus failed/stale/manual-review webhook ledger
  entries. Notify the responsible operator when a new case appears and escalate
  unresolved cases after 15 minutes. Flagged rows are excluded from normal expiry,
  and a successful batch does **not** mean that reconciliation is clear.
- Assign an incident owner and an escalation contact before launch. Investigate
  connection, permission, Stripe availability or inventory inconsistencies before
  retrying. Never compensate with unconditional stock increments or flag resets.

The queue/backlog monitors and alert delivery are requirements to implement or
configure later; the runner currently reports batch counts and exit status only.

## Minimum manual reconciliation procedure

Orders with `needsReconciliation` or `reconciliation_required` must remain blocked
for fulfillment and payouts until a verified, audited resolution. Do not clear
flags or bypass `orderInvariants` to make a shipment/payout proceed.

1. Open an incident with order ID, reservation/payment state, reason, relevant
   webhook event IDs and timestamps. Restrict access to the operational record;
   exclude credentials, client secrets, correlation tokens and customer address.
2. Inspect the existing order and its bound Stripe Session/PaymentIntent in the
   correct account and mode, initially read-only. Check owner, metadata binding,
   amount, currency and definitive payment status. An unknown intent or ambiguous
   network outcome is not evidence that no payment exists. Do not create a new
   intent or re-reserve/release stock to resolve that ambiguity.
3. For `processing` or an unknown outcome, retain the reservation and blocks;
   investigate delivery/retry of the existing financial event. A verified signed
   event through the financial coordinator can resolve the existing reservation;
   recording a paid state manually is prohibited.
4. For definitive cancellation, review the permitted lifecycle release and its
   evidence. For success after inventory release, review actual inventory and
   payment together and choose an explicitly authorized fulfillment/stock
   resolution or refund. Do not decrement/release stock again blindly. Refunds,
   event replays and every other external write require separate authorization.
   A refund alone is not permission to clear reconciliation or payout blocks.
5. Record approver/operator, evidence references, before/after state, authorized
   action, idempotency reference and outcome. There is currently no dedicated
   administrative resolver: if the existing guarded lifecycle cannot resolve the
   case, stop and prepare a reviewed resolution tool with tests and audit logging.
   Do not use raw Mongo updates, disable query guards or invent historical binding.
6. Close only after read-only verification of payment, reservation/stock and the
   applicable fulfillment/payout blocks, linking the financial event or resolution
   audit. Until then keep the case open and the order blocked.

Before returning inventory with an attempted/known intent, Stripe must confirm
final cancellation outside the Mongo transaction. `succeeded`/`processing` never
release inventory just because expiry time passed. Signed success subsequently
consumes the reservation, even if its nominal expiry passed.

If an attempted intent has unknown ID/outcome, inventory stays reserved and the
reconciliation flag explains why. Retry before expiry repeats the same Stripe key
and recovers the intent; a known ID clears that unresolved-preparation flag. After
expiry the system refuses new creation and requires reconciliation of the existing
Stripe outcome (metadata order ID). It must not release or recreate blindly. A
permanent Stripe invalid-request rejection without known successful intent can
release immediately; idempotency-key-in-use/network/ambiguous errors cannot.

Late legitimate signed success after inventory already released still marks paid,
flags `reconciliation_required` and blocks payouts; it never hides the discrepancy
or silently takes stock allocated to someone else. An operator must reconcile or
refund through a separately authorized procedure. Payment failures with a retryable
PaymentIntent retain reservation until definitive cancellation/expiry.

## Mobile recovery and cancellation

Authenticated GET `/api/stripe/checkout-intent` uses the key header and returns
public buyer order DTO, reservation state/expiry and reconciliation flag. It exposes
no PaymentIntent/customer IDs, hashes, tokens, client credentials or financial costs.
Authenticated POST `/api/stripe/checkout-intent/cancel` explicitly requests definitive
cancellation; it cannot command reservation state or stock. Stripe confirmation is
required. Unknown/processing/paid outcomes retain or finalize the existing purchase.

Dismissing PaymentSheet is not definitive cancellation: preserve cart and key and
allow retry of that same intention. The new explicit cancellation control only
rotates key after backend confirms release/completion. If validation/stock rejected
before any order existed, data can be corrected using the same unbound key.
PaymentSheet success stores the submission flag and uses received/verifying UX.
Remount can recover submitted intent without entering shipping again. An old paid
order does not delete a different current cart; digests must match for cleanup.

## Phase 4B: audited invariants

Financial late success is restricted to the signed webhook coordinator. A backend
32-byte random correlation value is stored in the order transaction before Stripe
work, and carried in PaymentIntent metadata. All managed financial events validate
order, correlation, owner, amount, currency and any previously bound intent/session.
Charge/refund handlers resolve PaymentIntent metadata when necessary. Invalid
correlation changes neither the order nor inventory; only webhook processing audit
records the rejection. Correlation is excluded from ordinary queries/serialization
and redacted from accidental logs. Existing historical orders are not backfilled.

A single-use in-memory document capability permits the real Mongoose financial
hook to accept failed -> paid only after the coordinator validates correlation.
Payment after release does not decrement again: it records paid plus
reconciliation_required/needsReconciliation and blocks payout and fulfillment.
Client/admin payment routes do not receive that capability. Reserved consumption
and release saves add expected reservation/payment state filters through Mongoose
$where, inside the same transaction as inventory. The Counter uses the document's
session; existing order numbers remain unchanged.

Admin/seller absolute stock or stock-management edits check active reservations
inside a transaction and write the product in that transaction, conflicting with
concurrent reservations. Relevant reserved managed lines return STOCK_RESERVED
409. Omitted stock/stock-management fields are preserved. This is a conservative
protection, not a warehouse adjustment subsystem.

The Next products page is a real consumer of /api/stripe/checkout. That endpoint now
requires existing cookie authentication and Idempotency-Key, and uses the same
reservation/idempotency/pricing coordinator with Stripe Checkout as its adapter.
Web identity is namespaced to the authenticated Mongo user; the order retains its
usuario for existing history/authorization. The legacy controller is retained but
returns 410 before executing any historical order/Stripe writes. Its alternative
/api/pagos routes remain unmounted. Next retains its intention in sessionStorage,
collects the same required delivery fields, and offers owner-verified recovery and
cancellation. Checkout displays one authoritative order total (including backend
shipping/tax/discount), not independently priced browser line items. Web cancellation
expires an open Checkout Session before checking/canceling its PaymentIntent;
processing/succeeded remain conservative. Managed orders do not sync to Firestore.

No runner was scheduled and no external integration was exercised. Deployment
still requires a transaction-capable topology and real Stripe event/race integration
under separate authorization. Unknown expired outcomes remain operator cases.
Historical orders without opaque correlation retain their prior handling and bound
Stripe identity checks; adding correlation to existing external intents requires a
separate reconciliation procedure. A payment retry after a prior financial failure
may retain an existing conservative payout block; no automatic unblocking policy
was introduced here.

## Phase 4C: financial scope, query guard and historical policy

Financial authorization now uses withAuthorizedFinancialTransition(document,
callback). The WeakSet capability exists only during the awaited callback, is
consumed by the financial pre-save hook, and is unconditionally removed in finally,
including validation/middleware/driver failures. No grant function/token/boolean
is exported. Production callers are settlePaid and the explicit financial
coordinator used by the verified webhook.

Generic order updateOne/updateMany/findOneAndUpdate (including findByIdAndUpdate)
reject protected financial/lifecycle fields for direct updates and operators,
including unset/rename destinations. Pipelines, whole-document replacements and
query upserts are conservatively prohibited. The bulkWrite wrapper applies the
same guard and rejects bulk inserts/replacements that bypass document creation
hooks; no bypass option exists. Nonfinancial audit/history and existing payout
ledger query updates continue working. There are no production financial bulk
callers. Raw driver access is not a supported application financial API.

Webhook paid/failure/refund updates now use document saves through the explicit
financial coordinator, rechecking binding and financial state in a Mongo
transaction with expected-state filters. Managed paid events still use settlePaid
so inventory consumption/reconciliation is unchanged. Failure does not erase
persisted Stripe binding. Invalid refund/state combinations require manual review.

Legacy order + exact stored Stripe binding: processing is permitted after matching
stored PaymentIntent to the event, or stored Checkout Session to a session event,
and validating amount/currency. Legacy order + no exact binding: no financial,
inventory, payout or fulfillment effects. The existing WebhookEvent ledger records
skipped plus a safe manual-review reason, with ordenId removed; HTTP 200 prevents
endless Stripe redelivery. Missing order/managed correlation also fails closed to
manual review. No historical correlation is invented or migrated. New managed
orders retain opaque correlation enforcement; policy does not weaken it.

The final state-writer audit leaves: pending initialization; transactional lifecycle
release/managed success; the signed webhook financial coordinator for legacy
success and managed/legacy failure/refund; model transition methods; and existing
admin non-Stripe transitions which explicitly prohibit marking paid. Unmounted
legacy checkout/webhook/controller functions remain inspection-only candidates and
must not be reactivated without migrating to this coordinator. Query writes left
in webhook and payout paths are audit/history ledger effects, not financial-state
updates. No production raw collection financial writer was found.

## Expiration reconciliation race correction (local only, 2026-10-03)

Batch selection is not a claim or lock. Before any cancellation through the Stripe
adapter, `cancelOrder` re-reads the persisted order and requires a reserved inventory
reservation, `needsReconciliation !== true`, payment state `pendiente` or `fallido`,
and a checkout state other than `completed`/`terminal`. Missing, already consumed,
released, paid/refunded, incompatible or flagged orders are left unchanged.

`release` repeats those checks inside its transaction, before any stock increment.
Its conditional save also requires `inventoryReservation.needsReconciliation` not
to be true. Transaction conflicts or failed conditional saves roll back inventory
restoration; the existing Stripe evidence checks remain required. A concurrent
review does not authorize release, and an uncertain Stripe result does not replace
a review reason that was already persisted. `succeeded`, `processing` and unknown
statuses keep the reservation and request reconciliation where eligible; an adapter
exception preserves stock and contributes a failed row to the batch result.

These checks are not a distributed lock or an atomic MongoDB/Stripe operation.
A change after the pre-cancellation read can still coincide with a Stripe request
already starting or in flight. The transactional release guard preserves local
stock in that case; this delivery does not claim to undo a remote cancellation.
A verified payment that wins locally consumes the reservation. A verified payment
arriving after a committed release still enters reconciliation and blocks payouts.

## Payout uncertainty correction — local only (2026-10-04)

This correction does not activate payouts, workers or the expiry scheduler. No
remote transfer, refund, database or configuration operation was performed.

### Obligation identity and durable claim

One existing order/vendor payout row represents one obligation. Its identity is
`payout_obligation_<orderId>_<vendorId>`, independent of event/admin/scheduler
`runId`. Stripe receives that identity as its idempotency key and metadata;
amount, currency and destination are recorded in the claim. Administrative run
information belongs to the local audit, not changing Stripe request parameters.
This is not a mechanism to issue additional obligations for the same order/vendor.
The individual transfer request disables Stripe SDK network retries; no new attempt
is scheduled after an ambiguous response.

Before Stripe, a conditional Mongoose update appends the claim to the existing
order history, increments the existing `__v`, and requires majority
acknowledgement. The predicate checks financial eligibility and exact history and
payout row snapshots. Competing claims cannot both match those snapshots. Version
increments also fence stale document saves through the model's existing
optimistic concurrency. No schema field, enum, index or financial query bypass
was added. Query updates only change history, version and Mongoose timestamps.

An unresolved claim is an INCIERTO signal even when the payout row still says
`pendiente` (e.g. interruption immediately after claiming). The service and admin
retry endpoint reject it. Eligibility also rejects `payoutBlocked`,
`needsReconciliation`, `reconciliation_required`, processing rows, uncertainty
metadata and historical non-paid rows with a processing timestamp or Transfer ID.
An unverified/missing order version fails closed. Historical attempt markers need
manual review; this correction does not invent proof that a transfer failed.

After the claim, conditional document saves retain payment, fulfillment and
reconciliation predicates. A fresh pre-transfer read checks the row and captured
amount/currency. A successful response is acknowledged locally only after the
paid row/Transfer ID is saved and a majority-acknowledged `_confirmed` history
entry is appended. Claim records are never removed or automatically reused.

Any error after claiming is conservatively uncertain, including an apparently
definitive Stripe rejection, malformed response, paid-save failure or failed
confirmation acknowledgement. The service attempts to persist `payoutBlocked`,
`needsReconciliation` (preserving an existing reason), existing `bloqueado` row
states and `meta.outcome: uncertain`. A known Transfer ID is retained for review.
Errors use fixed codes, not original Stripe/driver messages. If this persistence
also fails, the durable unresolved claim remains the eligibility barrier; the
administrative reconciliation queue may not show a new case until its flags can
be persisted. The caller must retain an operational incident for that error.

### Manual review before any resolution or retry

1. Open an incident identifying the order/vendor obligation and failed stage.
   Retain the claim, Transfer ID if known, captured amount/currency/destination,
   and operator/approver evidence. Do not record credentials or full documents.
2. With separately authorized read access to the correct Stripe account/mode,
   verify an existing Transfer by its known ID or obligation metadata and transfer
   group. Compare amount, currency, destination and any reversal with the local
   obligation. Review the bound payment and refunds independently: an accepted
   charge does not prove a vendor transfer, and a vendor transfer is not a bank
   payout.
3. If a matching transfer exists, reconcile its evidence/local recording; do not
   create another transfer. If the outcome remains unknown, retain all blocks.
   An empty search alone is not proof of nonexecution or permission to retry.
4. If nonexecution is conclusively established, any resolution/retry still needs
   a separate reviewed and authorized financial procedure. This delivery exposes
   no resolver, automatic replay, refund or reversal. Clearing flags or closing
   an administrative review does not retire the claim or authorize a transfer.
5. Record the audited before/after decision and verify every remaining obligation
   before clearing any order-level block. Never remove the claim to make a retry
   work or generate a fresh run-based financial identity.

## Discovering unconfirmed payout claims — local only (2026-10-04)

The existing administrative reconciliation queue now selects an order when its
history contains a valid `payout_obligation_<orderId>_<vendorId>` without the exact
`<obligationId>_confirmed` entry, even if no reconciliation or payout block flag
was persisted. The claim must bind to that same order. Confirming another vendor
or order does not clear it. A confirmation represents the existing service's
persisted acknowledgement; it is not a fresh verification against Stripe.

The read DTO labels these cases **Resultado de payout pendiente de verificar**.
Each pending obligation exposes only order/vendor IDs, obligation ID, claim date,
amount in cents, currency and destination account ID. Missing/invalid metadata is
shown as null, not invented or used to hide the claim. Full histories, arbitrary
metadata, addresses, secrets and driver messages are excluded. Both readers use
the same candidate expression, source projection, DTO and coverage metadata.
Audit snapshots retain the same redacted evidence. A changed set of pending
obligations changes the observed source version and requires a fresh review.

Closing a review changes only administrative records. It neither removes the
claim nor confirms a Transfer, clears financial/reservation blocks or authorizes
another payout. An operationally pending order is still selected by the live
source branch even if its administrative review is closed. A process interrupted
before Stripe and one interrupted after Stripe accepted a transfer can leave the
same claim: these reads deliberately do not classify either as failed.

### Queue coverage and limits

The queue is paginated by source case (one order, potentially several obligations),
not by obligation. All valid unconfirmed obligations of a returned order appear
in its source/detail; no per-order truncation is introduced. The live candidate
match precedes grouping, status filtering, sorting and the items/total facet.
The total counts the selected cases before page slicing. The list remains a
single observational aggregation outside transactions, not a globally frozen
snapshot. The detail and its audits retain their existing snapshot reads.

For discovery, omit `status` and select `kind=order` or omit `kind`. An explicit
`kind=event` or administrative status filter intentionally excludes other cases;
`status=open` can exclude a still-operationally-pending order whose review is
closed. Responses expose the selected filters in `coverage`, distinguish
administrative closure from operational state, and report
`paginationWindowExceeded` when the filtered total exceeds the accessible window
for the chosen page size. Existing limits remain: page at most 1000, limit at most
100 and offset at most 10000. With limit 100, the accessible window is 10100 cases;
with limit 1, only 1000 pages/cases are accessible. Coverage does not count cases
excluded by explicit filters. An empty later page is not evidence of no pending
claims when total is nonzero.

Complete enumeration of an arbitrarily large queue is therefore **not guaranteed**.
If the window is exceeded, stop treating pagination as a complete inventory; a
separately reviewed retrieval strategy would be needed. This delivery adds no
index, cursor contract or unlimited query. History scans and regex/set membership
have costs that remain unmeasured. Existing execution budgets can return a
sanitized failure instead of results; no such failure certifies an empty queue.
Malformed/nonconforming historical claim names are outside this new predicate.

### Evidence and manual review

Local tests use synthetic expression evaluation, controlled repositories and
loopback HTTP to check absence of flags, exact/partial confirmations, before/after
Stripe interruption representations, privacy, admin authorization, closing a
review without changing financial sources, stale source versions, filtering and
pagination. Native/Mongoose parity checks use driver/persistence doubles; they do
not certify actual execution of the MongoDB expression, real concurrency,
performance, or Stripe state. No remote connection is performed.

Use the incident procedure above to check the correct Stripe account/mode,
obligation metadata, transfer group, amount/currency/destination and any known
Transfer ID. A search with no results in Stripe does **not**, by itself, prove that
a transfer never happened or authorize replay. Uncertain cases remain blocked;
this delivery implements no financial resolver or new transfer action.
