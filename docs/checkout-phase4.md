# Phase 4: persistent checkout and inventory reservation

## Inventory decision

`Producto.stock` remains available-to-sell inventory; `gestionStock=false` skips
physical reservation. No second stock collection/counter was introduced. Reuse of
the alternative controller's correct guarded `$inc` is centralized in
`inventoryReservation.js`. A Mongo session/transaction is mandatory. There is no
standalone/session-less fallback. The alternative controller now uses this helper.
All lines, the pending order and its reservation are committed together. Mongo
`withTransaction` retries transaction conflicts; no Stripe call is inside it.

## Persistent intent and indexes

App POST `/api/stripe/payment-sheet` sends `Idempotency-Key` alongside Firebase
Bearer authentication. UUID is generated by Expo Crypto, contains no identity and
persists in AsyncStorage per local Firebase user. Storage contains only UUID,
commercial-payload SHA-256 digest and submission flag, never address/token/secret.
Retries and remounts use the same key. Changes to input retain that key and are
rejected if Mongo already bound it to another payload. Explicit backend-confirmed
release/completion lets the next deliberate purchase generate a fresh key.

Order `_id` is the first 24 hex characters of SHA-256(JSON.stringify([UID,key])).
The existing Mongo `_id_` unique index arbitrates concurrent inserts on every
process; this is not `findOne` then unguarded `create`. Full key hash, verified UID
and normalized-payload hash are also checked to fail closed on collisions.
Addresses are trimmed, quantities combined and products sorted; coupon is uppercase.
Same key/different UID does not grant access to the other UID's order.

**New Mongo indexes: none.** `_id_` already exists and cannot contain duplicate IDs.
No historical orders or IDs are modified. A rare collision with historical data
fails owner/hash validation; never overwrites it. These deterministic ObjectIds no
longer encode creation time; use `createdAt` for chronology. No index/migration or
external command was executed. Expiration scans may need a separately reviewed
nonunique index for scale, not correctness. Order-number counter gaps from aborted
transactions are possible; no historical order is removed.

An intention is identified by its key: another device must carry/recover that same
key to join it. Local AsyncStorage does not automatically synchronize keys between
devices. A different newly generated key represents a different purchase, even if
items match. There is no claim of automatic cross-device cart-intent synchronization.

## Mongo and Stripe sequence

1. Normalize/hash payload and identify UID/key order.
2. In one transaction, find compatible existing order or validate Mongo products,
   calculate trusted prices, reserve each managed product with stock >= quantity,
   create pending order and reservation. Insufficient stock rolls everything back.
3. Persist Stripe attempt timestamp before external work.
4. Outside Mongo transaction create/replay Customer and PaymentIntent, each using
   stable Stripe idempotency keys derived from the persisted key hash. Request
   metadata/price/customer parameters remain stable, without fresh reqId/IP.
5. Persist PaymentIntent ID and amount. No client_secret is stored in Mongo.
6. Return only required PaymentSheet credential, order ID and pricing. Known
   intents are retrieved on replay; no new intent is created after reservation expiry.

Reservation defaults to 15 minutes, configurable by `CHECKOUT_RESERVATION_MINUTES`
(range 1–60). This bounds retry creation far below Stripe key-retention windows.
Permanent Mongo intent identity is not a TTL document and is never deleted.

## Reservation states

`none` (historical orders), `reserved`, `consumed`, `released`,
`reconciliation_required` (paid after release). Fields record reserved/expiry/
consumed/released dates, managed product quantities and release reason. The flag
`needsReconciliation` also represents unresolved Stripe preparation or a paid/
processing intent observed during expiration. Paid-after-release blocks payouts.

Release uses a transaction: read reserved state, restore all product quantities,
mark released/terminal. Two concurrent releases cannot restore twice. Financial
success and consumption happen in the same transaction; stock was already deducted
at reservation, so consume does not decrement it again. Duplicate signed success
or cancellation has no duplicate inventory effect. Refunded orders are not reverted
to paid by a later success event. Missing historical products make release fail
atomically instead of losing a partial restore.

## Expiration and failure safety

`getLifecycle().expire(100)` locates expired reservations. Operational CLI is
`node scripts/expire-checkout-reservations.js` from `backend-multi`. It is not
imported/started by HTTP, workers or a memory timer. A production scheduler must
invoke it repeatedly; no scheduler, worker or infrastructure was activated here.
Rows requiring reconciliation do not starve later ordinary expiration batches.
Runner returns checked/failed counts; failures retain inventory and are retryable.

Before returning inventory with an attempted/known intent, Stripe must confirm
final cancellation outside the Mongo transaction. `succeeded`/`processing` never
release inventory just because expiry time passed. Signed success subsequently
consumes the reservation, even if its nominal expiry passed.

If an attempted intent has unknown ID/outcome, inventory stays reserved and the
reconciliation flag explains why. Retry before expiry repeats the same Stripe key
and recovers the intent; a known ID clears that unresolved-preparation flag. After
expiry the system refuses new creation and requires reconciliation of the existing
Stripe outcome (metadata order ID). It must not release or recreate blindly. A
permanent Stripe invalid-request rejection without known successful intent can
release immediately; idempotency-key-in-use/network/ambiguous errors cannot.

Late legitimate signed success after inventory already released still marks paid,
flags `reconciliation_required` and blocks payouts; it never hides the discrepancy
or silently takes stock allocated to someone else. An operator must reconcile or
refund through a separately authorized procedure. Payment failures with a retryable
PaymentIntent retain reservation until definitive cancellation/expiry.

## Mobile recovery and cancellation

Authenticated GET `/api/stripe/checkout-intent` uses the key header and returns
public buyer order DTO, reservation state/expiry and reconciliation flag. It exposes
no PaymentIntent/customer IDs, hashes, tokens, client credentials or financial costs.
Authenticated POST `/api/stripe/checkout-intent/cancel` explicitly requests definitive
cancellation; it cannot command reservation state or stock. Stripe confirmation is
required. Unknown/processing/paid outcomes retain or finalize the existing purchase.

Dismissing PaymentSheet is not definitive cancellation: preserve cart and key and
allow retry of that same intention. The new explicit cancellation control only
rotates key after backend confirms release/completion. If validation/stock rejected
before any order existed, data can be corrected using the same unbound key.
PaymentSheet success stores the submission flag and uses received/verifying UX.
Remount can recover submitted intent without entering shipping again. An old paid
order does not delete a different current cart; digests must match for cleanup.

## Before real services / production

Verify transaction-capable Mongo replica set or sharded deployment and transactional
privileges (not attempted here). API fails closed on a standalone server; no partial
stock fallback. Configure reservation duration and separately schedule/monitor the
expiration runner. Establish monitoring/operations for reconciliation flags and
failed batches. Validate Stripe account/key/webhook wiring and request retries with
real infrastructure only under later authorization. Optional API workers remain
disabled. No external Mongo, Firebase, Stripe or Render call was made in this phase.

Tests use mock Stripe and a serializable rollback repository. They prove service
transitions/concurrency and guarded Mongo adapter arguments locally; they do not
replace an integration test against the eventual Mongo topology. The existing 25
security/configuration/checkout tests remain, with mock adapters updated for the new
persistent coordinator rather than invoking real infrastructure.

## Phase 4B: audited invariants

Financial late success is restricted to the signed webhook coordinator. A backend
32-byte random correlation value is stored in the order transaction before Stripe
work, and carried in PaymentIntent metadata. All managed financial events validate
order, correlation, owner, amount, currency and any previously bound intent/session.
Charge/refund handlers resolve PaymentIntent metadata when necessary. Invalid
correlation changes neither the order nor inventory; only webhook processing audit
records the rejection. Correlation is excluded from ordinary queries/serialization
and redacted from accidental logs. Existing historical orders are not backfilled.

A single-use in-memory document capability permits the real Mongoose financial
hook to accept failed -> paid only after the coordinator validates correlation.
Payment after release does not decrement again: it records paid plus
reconciliation_required/needsReconciliation and blocks payout and fulfillment.
Client/admin payment routes do not receive that capability. Reserved consumption
and release saves add expected reservation/payment state filters through Mongoose
$where, inside the same transaction as inventory. The Counter uses the document's
session; existing order numbers remain unchanged.

Admin/seller absolute stock or stock-management edits check active reservations
inside a transaction and write the product in that transaction, conflicting with
concurrent reservations. Relevant reserved managed lines return STOCK_RESERVED
409. Omitted stock/stock-management fields are preserved. This is a conservative
protection, not a warehouse adjustment subsystem.

The Next products page is a real consumer of /api/stripe/checkout. That endpoint now
requires existing cookie authentication and Idempotency-Key, and uses the same
reservation/idempotency/pricing coordinator with Stripe Checkout as its adapter.
Web identity is namespaced to the authenticated Mongo user; the order retains its
usuario for existing history/authorization. The legacy controller is retained but
returns 410 before executing any historical order/Stripe writes. Its alternative
/api/pagos routes remain unmounted. Next retains its intention in sessionStorage,
collects the same required delivery fields, and offers owner-verified recovery and
cancellation. Checkout displays one authoritative order total (including backend
shipping/tax/discount), not independently priced browser line items. Web cancellation
expires an open Checkout Session before checking/canceling its PaymentIntent;
processing/succeeded remain conservative. Managed orders do not sync to Firestore.

No runner was scheduled and no external integration was exercised. Deployment
still requires a transaction-capable topology and real Stripe event/race integration
under separate authorization. Unknown expired outcomes remain operator cases.
Historical orders without opaque correlation retain their prior handling and bound
Stripe identity checks; adding correlation to existing external intents requires a
separate reconciliation procedure. A payment retry after a prior financial failure
may retain an existing conservative payout block; no automatic unblocking policy
was introduced here.

## Phase 4C: financial scope, query guard and historical policy

Financial authorization now uses withAuthorizedFinancialTransition(document,
callback). The WeakSet capability exists only during the awaited callback, is
consumed by the financial pre-save hook, and is unconditionally removed in finally,
including validation/middleware/driver failures. No grant function/token/boolean
is exported. Production callers are settlePaid and the explicit financial
coordinator used by the verified webhook.

Generic order updateOne/updateMany/findOneAndUpdate (including findByIdAndUpdate)
reject protected financial/lifecycle fields for direct updates and operators,
including unset/rename destinations. Pipelines, whole-document replacements and
query upserts are conservatively prohibited. The bulkWrite wrapper applies the
same guard and rejects bulk inserts/replacements that bypass document creation
hooks; no bypass option exists. Nonfinancial audit/history and existing payout
ledger query updates continue working. There are no production financial bulk
callers. Raw driver access is not a supported application financial API.

Webhook paid/failure/refund updates now use document saves through the explicit
financial coordinator, rechecking binding and financial state in a Mongo
transaction with expected-state filters. Managed paid events still use settlePaid
so inventory consumption/reconciliation is unchanged. Failure does not erase
persisted Stripe binding. Invalid refund/state combinations require manual review.

Legacy order + exact stored Stripe binding: processing is permitted after matching
stored PaymentIntent to the event, or stored Checkout Session to a session event,
and validating amount/currency. Legacy order + no exact binding: no financial,
inventory, payout or fulfillment effects. The existing WebhookEvent ledger records
skipped plus a safe manual-review reason, with ordenId removed; HTTP 200 prevents
endless Stripe redelivery. Missing order/managed correlation also fails closed to
manual review. No historical correlation is invented or migrated. New managed
orders retain opaque correlation enforcement; policy does not weaken it.

The final state-writer audit leaves: pending initialization; transactional lifecycle
release/managed success; the signed webhook financial coordinator for legacy
success and managed/legacy failure/refund; model transition methods; and existing
admin non-Stripe transitions which explicitly prohibit marking paid. Unmounted
legacy checkout/webhook/controller functions remain inspection-only candidates and
must not be reactivated without migrating to this coordinator. Query writes left
in webhook and payout paths are audit/history ledger effects, not financial-state
updates. No production raw collection financial writer was found.
